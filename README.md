# ticketing-lab

> 필요해진 것만 그때 도입하며 만드는 **Spring Boot 학습 프로젝트**

공연 좌석을 조회하고 예매하는 API 서버입니다.
기능 완성이 아니라 **무엇을 왜 그렇게 만들었는지**를 남기는 것이 목적입니다.

세 가지 원칙으로 진행합니다.

- **기술은 필요해진 뒤에 도입한다.** 무엇을 쓸지 미리 정해두지 않는다.
- **모든 설계 결정에는 포기한 선택지가 있다.** 그 기록을 [ADR](docs/adr/)에 남긴다.
- **혼자 하지만 혼자 결정하지 않는다.** 모든 변경은 이슈 → 브랜치 → PR을 거친다.

---

## 기술 스택

`Java 21` `Spring Boot 4.1` `Spring Data JPA` `MySQL 8` `Gradle` `Docker Compose` `JUnit5`

스택은 고정된 목록이 아닙니다. 필요해질 때마다 추가하고, 왜 추가했는지는 [ADR](docs/adr/)에 남깁니다.

---

## 진행 방식

미리 짜둔 로드맵은 없습니다.

기능을 하나 만들고 → 막히거나 느려지는 지점을 찾고 → 왜 그런지 파악한 뒤에 → 도구를 도입합니다.
도입한 이유와 포기한 선택지는 [ADR](docs/adr/)에, 측정한 숫자는 [학습 로그](docs/learning-log.md)에 남깁니다.

**지금 다루고 있는 것: 엔티티 설계와 트랜잭션**

---

## 도메인 모델

설계 중입니다. 확정되는 대로 ERD와 함께 채웁니다.

---

## 실행 방법

```bash
# 1. DB 기동
docker compose up -d

# 2. 애플리케이션 실행
./gradlew bootRun
```

API 명세는 실행 후 Swagger에서 확인할 수 있습니다. → http://localhost:8080/swagger-ui.html
호출 예시는 `http/` 디렉터리의 `.http` 파일을 참고하세요.

## 개발 컨벤션

혼자 하는 프로젝트지만 **모든 작업은 이슈 → 브랜치 → PR**을 거칩니다.
협업 흐름을 몸에 익히는 것도 이 프로젝트의 목표 중 하나입니다.

### 타입

| 타입 | 설명 |
|---|---|
| `feat` | 새로운 기능 추가, 요구사항에 맞춘 기존 기능 수정 |
| `fix` | 버그 수정, 예외 처리 |
| `refactor` | 기능 변화 없는 코드 구조 개선 (변수명 변경 등) |
| `docs` | 문서·주석 수정 (README, API 명세 등) |
| `test` | 테스트 코드 작성 |
| `style` | 코드 스타일, 포맷팅 |
| `build` | 빌드 관련 수정 |
| `chore` | 설정, 패키지, `.gitignore` 등 기타 |
| `release` | 버전 릴리즈 |
| `merge` | 병합 |

### Issue

- **제목**: `[BE] Feat: 개발 기능` — 예) `[BE] Feat: entity 생성`
- **내용**: 이슈 템플릿에 맞춰 작성
- **라벨**: `BE`, `기능추가`, `리팩토링`, `에러`, `문서` 등

### Branch

- 모든 브랜치는 **`dev`에서 생성**합니다
- **기능 단위**로 생성하고, 완료되면 PR을 올립니다
- 머지 후 브랜치를 **삭제**합니다 (Delete branch)

**네이밍**: `타입/작업내용/이슈번호`

| 작업 내용 | 브랜치명 |
|---|---|
| entity 구현 | `feat/entity-add/1` |
| 예매 금액 버그 수정 | `fix/reservation-price-bug/2` |
| JPA 설정 변경 | `chore/jpa-config/3` |

### Commit

```bash
git commit -m "[Feat] 예매 생성 API 추가"
```

### Pull Request

- **자주 커밋하고, PR도 자주 올립니다.** 한 번에 몰아 올리면 스스로도 알아보기 힘듭니다
- **제목**: `[Feat] 핵심적인 부분만 간략하게`
- **내용**: PR 템플릿에 맞춰 작성
- **라벨**: 이슈와 동일
- 머지 전 스스로 리뷰하고 테스트를 통과시킵니다

**PR 본문 템플릿**

```markdown
## 무엇을
## 왜 이렇게 (다른 선택지와 비교)
## 막혔던 것 / 어떻게 풀었나
## 확신 없는 부분
```

마지막 항목을 비워두지 않습니다. 그게 리뷰와 [ADR](docs/adr/)의 출발점입니다.
